# Survey of Multi-Agent Pentesting Architectures  

Autonomous AI-driven pentesting systems (like XBOW) use multiple specialized agents under a coordinating controller, tool APIs, and strict validation to reliably discover vulnerabilities.  Recent open-source projects (PentestGPT, PenHeal, MAPTA) have demonstrated the promise and pitfalls of LLM-based approaches.  PentestGPT (USENIX’24) uses three cooperating LLM modules to sequentially enumerate, exploit, and escalate, addressing context loss by modular design.  PenHeal proposes a two-stage LLM pipeline (vulnerability discovery + remediation) using counterfactual prompting and an “instructor” module to explore multiple attack paths.  MAPTA (arXiv’25) implements a **three-role multi-agent architecture**: an LLM *Coordinator* for high-level planning, multiple LLM *Sandbox* agents for tactical execution, and a *Validator* for proof-of-concept testing.  These works show that purely LLM-based scans produce many false positives, so they integrate deterministic validation (tool calls, Docker sandboxes) to check every finding.  XBOW’s own reports stress that **unstructured LLM-only testing is unreliable**: “you can’t just wrap an LLM and call it a pentest” – a governed system with coordination, overlap-avoidance, and continuous validation is required.  

Key insights from these references: (1) Use **multi-agent orchestration** with distinct roles (coordinator, executor, validator). (2) Equip LLM agents with explicit tool interfaces (e.g. `run_command`, `run_python`) as in ReAct/Toolformer paradigms so they interact safely with the environment. (3) Break tasks into small verifiable steps (e.g. find endpoint then verify, find object then verify) to avoid LLM hallucinations. (4) Provide safety guardrails: restrict agent motives, tool access, and perform just-in-time permission checks. (5) Measure performance rigorously: MAPTA accounted token and API costs and success rates across the 104-challenge XBOW benchmark. This open-science approach (sharing code, benchmarks) contrasts with XBOW’s closed systems.  

# Algorithmic Hybridization (Q12–Q15)  

- **Largest Improvement:**  In practice, the **hybrid approach** of combining LLM reasoning with classical security algorithms yields the biggest gains.  For example, an open-source agent (“Deadend”) achieved 78% on the XBOW CTF by using *recursive task decomposition* and feedback loops: when a tool failed, an LLM could direct a sub-agent to try alternative strategies, iterating until success.  In general, one should fuse:  
  - **LLM-based planning & reasoning** (for hypothesizing vulnerabilities, crafting exploits, summarizing context)  
  - **Deterministic scanning/fuzzing** (port scanners, active crawlers, payload fuzzers) to guarantee coverage  
  - **Symbolic/static analysis** (AST inspection, taint analysis, constraint solving) to pinpoint logic flaws  
  - **Knowledge/Graph methods** (to model network/application topology and previously-seen vulnerabilities)  
  - **Reinforcement learning or search** (to optimize long-horizon attack chains or prioritize actions)  
  - **Multi-agent consensus** (using multiple parallel agents to cover state space)  
  - **Feedback loops** (validate hypotheses via execution and refine plans).  

  This multi-algorithm mix leverages LLM creativity for open-ended reasoning while relying on proven deterministic engines for grunt work.  For instance, MAPTA uses LLMs for strategy but invokes concrete tools (`nmap`, `python`, etc.) under orchestration.  PenHeal shows that integrating *counterfactual prompting* (to force LLMs to consider “what-if” attack paths) and an instructor for external knowledge can improve coverage.  Overall, the “largest expected improvement” comes from **structured LLM guidance + deterministic verification**: e.g. LLM suggests an exploit, classical tools attempt it, and validation confirms success (so false positives are immediately caught).  

- **Deterministic Components (Q13):**  Functions requiring reliability and repeatability should be **algorithmic**.  This includes attack-surface enumeration, vulnerability probing, and result aggregation.  XBOW explicitly uses *deterministic logic* to “debrief agents, refine findings, and prioritize next actions” – essentially, the coordinator merges all agent reports via hard-coded rules.  Similarly, port scans, static code analysis, pattern matching, and impact calculations should be handled by fixed algorithms, not LLM conjecture.  For example, verifying an endpoint exists or an IDOR is accessible is done via scripted checks, not by the LLM’s word.  In MAPTA, every candidate exploit is concretely executed in a Docker sandbox (deterministic step) rather than relying on the LLM’s claim.  In short, **decision-making, logging, and validation pipelines** remain deterministic, ensuring repeatable, audited outcomes.

- **LLM-Delegated Tasks (Q14):**  Tasks that benefit from flexible reasoning or natural language understanding can be handled by LLM agents.  These include: strategic planning (e.g. “what attack vector should we try next?”), hypothesizing multi-step exploits, translating observed behavior into hypotheses, and generating exploit payloads or scripts.  In MAPTA, both the Coordinator and Sandbox roles are LLM-driven: the Coordinator LLM “performs attack-path reasoning, tool orchestration, and report synthesis,” while Sandbox LLMs use the `run_command`/`run_python` tools to execute LLM-generated tactics.  Similarly, an LLM might analyze subtle error messages or logs and propose new payloads.  We would delegate **creative, open-ended intelligence tasks** to the LLM: generating candidate vulnerabilities, designing fuzz payloads, summarizing results for human analysts, and deciding high-level strategy, letting it use external tools as subroutines.

- **Never Delegate (Q15):**  Anything safety-critical or highly precise must not be left to an LLM’s subjective judgment.  LLMs *hallucinate* and lack guaranteed correctness, so they should **never be the sole arbiter of exploit validity or the executor of dangerous actions**.  For example, final exploit execution on production systems, handling private keys or sensitive data, or any action that could irreversibly damage the target must not rely on an LLM without strict checks.  As XBOW warns, “LLM agents alone have unpredictable behavior that will hallucinate exploits, and they don’t have any ground truth validation”.  Therefore, any action with potential harm must be mediated by deterministic code.  In practice, the LLM can propose an attack, but a safe wrapper must vet it.  We also avoid delegating **resource accounting, stopping criteria, or monitoring** to LLMs – these are best kept in code.  In summary: **LLMs may advise and plan, but execution and policy enforcement remain deterministic**.

# DOGE vs XBOW: Key Differences (Q16–Q17)  

To be *fundamentally different* and scientifically novel, DOGE should **not simply mirror XBOW’s blueprint**.  Possible differentiators include: 

- **Modular Learning & Adaptation:** Instead of fixed orchestration rules, DOGE might incorporate **reinforcement learning** or meta-learning so agents improve over time.  For example, a DOGE Planner could learn which attack chains tend to work across targets, adjusting priorities adaptively.  This contrasts with XBOW’s mainly one-shot planning.

- **Symbolic / Causal Integration:** Embedding a **knowledge graph or symbolic reasoning layer** (e.g. logic constraints, program analysis) could give DOGE causal insight into why vulnerabilities occur.  XBOW relies on LLM pattern recognition; DOGE could integrate static analysis results (e.g. AST graphs) so the system reasons about causes of bugs.  For instance, if an LLM proposes an exploit chain, a symbolic checker can verify whether the conditions truly allow it (causal validation).

- **Multi-paradigm Agents:** DOGE could combine heterogeneous agents: not just LLM-driven ones but also purely statistical or formal agents.  For example, a Bayesian scanner agent that updates a probabilistic model of the target as it probes, feeding into the LLM’s next prompt.  This fusion could generalize better than XBOW’s all-LLM approach.

- **Open and Interpretable Design:** XBOW is proprietary. DOGE should strive for open architectures and reproducible benchmarks, making its design scientifically transparent.  By providing code, logs, and well-defined benchmarks, DOGE would allow rigorous analysis and community validation, unlike the opaque descriptions of XBOW.

- **Domain-General Framework:** XBOW is focused on web/CTF pentesting. DOGE’s architecture could be designed more generally (e.g. network, application, or IoT exploits) by abstracting the problem. Scientific interest would grow if DOGE works across domains (not just the web) by learning domain-independent patterns of vulnerabilities.  

- **Mathematical Foundations:** To be interesting, DOGE could ground its methods in theory: e.g. treat the target as a POMDP or a causal Bayesian network, using algorithms from operations research (like belief-space planning) in tandem with LLM heuristics.  This is different from XBOW, which offers few formal guarantees.  If DOGE comes with provable performance bounds (e.g. on coverage vs cost) or converges to optimal policies under certain assumptions, that would be genuinely novel.

- **Human-in-the-Loop Safety:** Finally, DOGE might innovate in governance. Perhaps it uses human feedback or automated audits at key steps to ensure safe exploration.  XBOW implicitly enforces safety through hardcoded guardrails, but DOGE could learn to obey constraints or have an LLM ethics checker.  

In summary, DOGE should blend LLMs with new algorithmic ideas (RL, symbolic AI, structured planning) to go beyond XBOW’s current capabilities. It becomes scientifically interesting if it, for example, **automatically discovers new vulnerability types, generalizes to unseen systems, or provably reduces attacker effort** by applying causal/learning methods that XBOW does not use.

# Experimental Validation (Q18–Q19)  

- **Proving it Works (Q18):**  We must design rigorous benchmarks.  A natural experiment is to run DOGE on **established pentest challenges** (e.g. the 104 XBOW CTF tasks, DVWA, OWASP Juice Shop, or real open-source web apps) under the same constraints.  Metrics would include *vulnerability coverage* (percent of known exploits found), *false positive rate*, and *resource usage* (time, API cost).  For example, MAPTA reports a 76.9% success rate on XBOW tasks; we would compare DOGE’s success percentage to XBOW/MAPTA and to human baselines under identical conditions.  We’d also measure **efficiency** (similar to MAPTA’s token-cost analysis) and **reliability** (e.g. run multiple trials with different random seeds and measure variance).  Statistical tests (e.g. bootstrapped confidence intervals or t-tests) would determine if any performance gains are significant.  

  Crucially, we need **end-to-end proof-of-concept exploits** for each finding.  A successful experiment might show that DOGE finds X% more true vulnerabilities than XBOW/MAPTA on a hold-out set, or finds the same bugs with 30% fewer API calls, etc.  We should also track *novel discoveries*: if DOGE uncovers real CVEs in live open-source software (as MAPTA did with 19 real vulns), that strongly validates its power.  A thorough protocol would document DOGE’s hyperparameters, random seeds, and use statistical significance to rule out chance.  

- **Proving it Fails (Q19):**  We must also identify clear failure cases.  One approach is *ablations*: remove or disable DOGE’s new components (e.g. turn off the RL planner or the static analysis module) and show performance drops back to baseline – this highlights the necessity of each part.  Another is to test DOGE on *adversarial benchmarks* designed to be hard for its methods.  For instance, MAPTA reports near 0% on blind SQL injection; if DOGE still fails blind-SQL tasks in our tests, that suggests a fundamental weakness.  We can also vary parameters: if DOGE’s performance is extremely sensitive to its LLM accuracy or hyperparameters, showing that degradation under small changes means it’s brittle.  Finally, run statistical tests to check for negative results: if DOGE consistently underperforms XBOW/MAPTA on key metrics (e.g. lower true positive rate or higher false positives with p<0.05), we must conclude the new design doesn’t outperform existing.  Overall, an experiment “proving it doesn’t work” would highlight a *systematic gap*, such as inability to handle certain vulnerability classes or lack of generalization.

# Proposed DOGE Architecture (Q20)  

Based on these insights, a promising DOGE design would be a **hybrid multi-agent system** combining LLM reasoning with deterministic modules:

- **Multi-Agent Structure:** Like MAPTA/XBOW, use a Coordinator agent (LLM) for global strategy and multiple Sandbox agents (LLMs) for focused execution.  However, add new roles: e.g. a *Static Analysis Agent* that uses symbolic methods to pre-scan code (white-box mode) and a *Learning Agent* that adjusts priorities based on feedback from past scans.  Each agent type has distinct tools. For example, the Sandbox LLMs use `run_command` (shell tools) and `run_python` as in MAPTA; the Static Agent invokes AST parsers and taint analyzers (deterministically) to flag common patterns; the Coordinator LLM uses a custom “plan” toolkit to hypothesize next targets.  

- **Tool API and Orchestration:** Provide each agent with a rich, but carefully controlled, toolset.  This might include: network scanners (nmap, ffuf), vulnerability scanners (sqlmap, Arachni), fuzzers, HTTP libraries, plus custom low-level tools (e.g. an extensible Playwright-based injector as in Deadend).  The Coordinator issues tasks via a deterministic orchestration layer (which could be a scheduler with a queue) that ensures agents don’t overlap in scope.  The global state (discovered hosts, credentials, found endpoints) is stored in a shared knowledge graph or database.

- **LLM Roles:** Use large LMs for the Coordinator and Sandbox roles. For example, the Coordinator’s prompt might include the attack history and environment description, asking “what should we try next?” The Sandbox agents receive sub-goals and respond with concrete commands or exploit snippets.  To ensure focus, each Sandbox agent gets a truncated context (as MAPTA does), preventing prompt bloat.  We might use chain-of-thought prompts internally to guide complex reasoning in the Coordinator.  

- **Deterministic Validation:** Every proposed exploit goes through a **Validator module** (could be a separate agent or function).  This component runs the exploit in a safe environment (Docker/container) and checks for success via side effects (captured output, flags, changes).  It returns a pass/fail.  Only validated exploits are reported.  This follows MAPTA’s proof-of-concept approach and XBOW’s multi-step verification.

- **Learning and Feedback:** Embed a learning loop.  For instance, use a simple reinforcement learner or a neural planner that observes which Coordinator choices led to valid exploits.  Over many runs (or across multiple targets), this learner biases the Coordinator’s future prompts (e.g. by adjusting the priority of certain actions).  This gives DOGE adaptability beyond fixed prompts.  We might store outcome statistics in the knowledge graph to drive this (e.g. if SQL injection succeeded 90% of time on similar apps, propose it earlier).

- **Safety and Governance:** DOGE should enforce the same guardrails XBOW uses: formalize the “motive, method, opportunity” rules.  The LLMs never receive unconstrained goals – prompts are carefully worded to prohibit illegal actions.  Tools are whitelisted per task, and all actions are logged and pre-authorized by deterministic policy.  For example, if an agent requests to exfiltrate data, the controller intercepts and denies it unless under the pen-test scope.  This layering of a deterministic safety net around the LLM is crucial (as XBOW recommends).

- **Mathematical Underpinning:** The core of DOGE can be viewed as a **Markov Decision Process**: at each step, the state (knowledge graph, credentials, responses) updates based on agent actions (tool calls).  The Coordinator’s LLM acts as a high-level policy, but the system also uses cost-performance analysis (like MAPTA’s resource accounting) to decide when to stop.  We could even formalize parts of DOGE as a POMDP if the target’s internals are partially observable.  For statistical validation, we treat DOGE’s success probability as a parameter to estimate (with confidence intervals) when comparing it to baselines.

**Why this architecture?** It unifies the best of both worlds: creative reasoning from LLMs and reliable algorithms for verification. The multi-role division has been shown effective, and adding a learning component and knowledge base aims at the *innovation* beyond XBOW. It addresses XBOW’s limitations (e.g. no open-source, no learning) and incorporates MAPTA’s rigorous validation. Alternatives (pure LLM “agent-as-a-service”, or solely RL-based pentesting) lack evidence of general success, whereas this hybrid is grounded in recent research.  

**Alternatives & Competitors:** A fully-RL approach (training an agent on a simulator) could, in principle, generalize, but it requires realistic simulators (expensive to build) and tends to struggle with real-world complexity. Pure symbolic analysis is fast but fails on zero-days. Future **fine-tuned LLMs specialized for security** (or larger models like GPT-6) might outperform DOGE’s LLM, and better unsupervised methods (like GANs for exploit generation) could also emerge. We should therefore design DOGE to be modular: the LLM component can be upgraded, or the rule-based parts replaced, as better algorithms appear.  

**Validation:** Ultimately, whether DOGE “works” is proven by rigorous testing. We would run our proposed experiments (Q18–Q19) to collect data on DOGE’s effectiveness and compare to baselines. If DOGE significantly beats or reliably matches XBOW/MAPTA metrics under controlled experiments, we have evidence of success. If not, the failure modes are instructive: for instance, if Doge still misses blind-SQL injections like MAPTA did, we would know further innovation is needed.  

In conclusion, the recommended DOGE system is a *coordinated multi-agent framework with both LLM-driven reasoning and deterministic verification*.  Its design draws on best practices (validation loops, safety), incorporates new elements (learning from experience, knowledge graphs), and would be validated by standard pentesting benchmarks.  This integrated approach maximizes novel discovery and generalization while maintaining causal understanding (through deterministic oracles), aligned with the goals of reproducible, efficient research into autonomous pentesting.
